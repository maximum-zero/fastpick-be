# 대용량 데이터 조회 성능 개선

## 요약

100만 건 데이터 환경에서 쿠폰 검색 API의 성능 병목을 재현하고,  
실행 계획 분석과 탐색 구조 변경을 통해 개선했습니다.

- 중간 일치 검색으로 Sequential Scan 발생
- B-Tree 인덱스를 활용할 수 없는 검색 조건 확인
- Keyword 전용 테이블과 전방 일치 검색 구조 적용
- Projection과 Redis Cache를 통한 추가 비용 감소
- p99 `60초 초과 → 154ms`
- Error Rate `약 75% → 0%`

---

## 1. 문제 재현

### 테스트 환경

- 데이터 규모: 100만 건
- 부하 테스트 도구: K6
- 테스트 범위: 100~200 VU

> 서버와 VM 사양은 [서버 인프라 구성도](https://www.notion.so/2f555588581980378187cd547219c018?source=copy_link)를 참고합니다.

### 발생한 문제

- 키워드 검색 시 p99 응답 시간 60초 초과
- Error Rate 약 75% 발생
- 부하 증가에 따라 처리량 급감

---

## 2. 원인 분석

기존 검색 API는 다음 조건을 사용했습니다.

```sql
LIKE '%keyword%'
```

검색어 앞에 와일드카드가 존재하기 때문에  
B-Tree 인덱스가 탐색 시작 지점을 특정할 수 없는 구조였습니다.

### 실행 계획 확인

`EXPLAIN (ANALYZE, BUFFERS)`를 사용해 실행 계획을 확인했습니다.

```sql
Parallel Seq Scan on tb_coupon c1_0
Filter: (((title)::text ~~ '%NIKE%'::text)
    AND ((use_status)::text <> 'ALL'::text))
Rows Removed by Filter: 285,781
Buffers: shared hit=15,277 read=19,132
```

실행 계획에서 `Parallel Seq Scan`이 발생하는 것을 확인했습니다.

### 분석 결과

- 검색 요청마다 전체 테이블을 순차 탐색
- 많은 행이 검색 조건 평가 후 제거됨
- 디스크 및 버퍼 I/O 부하 증가
- 동시 요청 증가 시 응답 시간이 급격히 증가
- 복합 인덱스를 추가해도 선행 와일드카드로 인해 핵심 병목이 해소되지 않음

---

## 3. 구조 변경

### 3-1. 검색 대상 분리

검색에 필요한 Keyword를 별도 테이블로 분리했습니다.

이를 통해 검색 대상과 조건을 명확하게 관리하고,  
쿠폰 전체 데이터를 직접 순차 탐색하는 구조를 변경했습니다.

### 3-2. 인덱스를 활용할 수 있는 검색 조건으로 변경

기존 중간 일치 검색:

```sql
LIKE '%keyword%'
```

변경한 전방 일치 검색:

```sql
LIKE 'keyword%'
```

전방 일치 검색으로 변경하여  
B-Tree 인덱스가 검색 시작 범위를 찾을 수 있도록 구성했습니다.

### 3-3. 조회 데이터 범위 축소

Projection을 적용하여 API 응답에 필요한 데이터만 조회했습니다.

- 불필요한 Entity 전체 로딩 방지
- 객체 변환 및 매핑 비용 감소
- 조회 결과의 메모리 사용량 감소

### 3-4. 반복 조회 부하 완화

동일한 검색 조건의 반복 요청에는 Redis Cache를 적용했습니다.

이를 통해 반복 검색 시 데이터베이스 접근 횟수를 줄였습니다.

## 5. 개선 과정에서 확인한 점

### 인덱스 추가만으로 해결할 수 없는 병목

검색 조건 자체가 인덱스를 활용할 수 없는 형태라면  
인덱스를 추가하는 것만으로는 성능을 개선하기 어렵습니다.

### 실행 계획 기반 분석의 중요성

쿼리 문장만 보고 판단하지 않고,  
실제 실행 계획과 버퍼 사용량을 확인해야 병목 구간을 정확하게 파악할 수 있습니다.

### 데이터 구조와 탐색 방식의 영향

검색 대상과 탐색 방식을 변경하는 구조적 개선이  
단순 옵션 조정보다 큰 성능 개선으로 이어질 수 있음을 확인했습니다.
