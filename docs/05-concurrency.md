# 선착순 쿠폰 발급 동시성 제어

## 요약

동시 1,000건 요청 환경에서 선착순 쿠폰 발급 시 발생하는
동시성 문제를 재현하고, 요청 처리 구조를 변경하여 개선했습니다.

- DB 락 기반 구조에서 락 경합 및 커넥션 대기 발생
- Redis Atomic Counter 기반 선착순 사전 판단
- Redis Queue와 Scheduler를 통한 비동기 저장 구조 적용
- 동시 1,000 VU 환경에서 초과 발급 0건 달성

---

## 1. 문제 재현

### 테스트 환경

- 동시 요청: 1,000 VU
- 부하 테스트 도구: K6
- 목표: 초과 발급 없이 안정적인 쿠폰 발급

> 서버와 VM 사양은 [서버 인프라 구성도](https://www.notion.so/2f555588581980378187cd547219c018?source=copy_link)를 참고합니다.

### 발생한 문제

- 동시 요청 증가에 따라 응답 지연 및 실패 증가
- DB 락 경합 발생
- 커넥션 풀 대기 증가
- 처리량 급감

---

## 2. 원인 분석

초기 구조는 DB 트랜잭션 내부에서
재고 확인과 발급 처리를 수행했습니다.

또한 Redis 분산 락을 사용하여
동일 쿠폰의 중복 처리를 방지했습니다.

### 초기 구조

- DB 비관적 락 기반 재고 차감
- Redis 분산 락 기반 중복 처리

### 분석 결과

- 동시 요청이 증가할수록 락 대기 시간 증가
- 트랜잭션 내부 경쟁으로 DB Connection 점유 시간 증가
- 커넥션 풀이 포화되며 처리량 급감
- 경쟁을 트랜잭션 내부에서 해결하는 구조 자체가 병목으로 작용

## 3. 구조 변경

### 3-1. Redis Atomic Counter 기반 선착순 판단

Redis Atomic Counter를 사용하여
트랜잭션 진입 전에 선착순 여부를 먼저 판단했습니다.

- 발급 가능한 요청만 Redis Queue에 적재
- 수량을 초과한 요청은 DB 접근 없이 즉시 실패 응답

> Redis의 원자적 증감 연산을 활용하여
> 동시 요청에서도 선착순을 일관되게 처리했습니다.

### 3-2. 요청 처리와 영속화 분리

API 요청 흐름에서는
Queue 적재까지만 수행하도록 변경했습니다.

이후 Scheduler가 Queue를 조회하여
발급 이력을 PostgreSQL에 저장하도록 구성했습니다.

```text
Client
   ↓
Redis Atomic Counter
   ├── 발급 불가 → 즉시 실패 응답
   └── 발급 가능
          ↓
     Redis Queue
          ↓
      성공 응답

Scheduler
      ↓
Redis Queue
      ↓
PostgreSQL
```

이를 통해 사용자 요청 처리와
DB 저장 작업을 분리했습니다.

### 3-3. 트랜잭션 범위 축소

DB 트랜잭션은
Scheduler가 Queue에서 가져온 발급 요청을
저장하는 구간으로 한정했습니다.

이를 통해

- DB Connection 점유 시간 감소
- 락 경합 감소
- 사용자 요청 처리 시간 단축

## 5. 개선 과정에서 확인한 점

### 락을 강화하는 것만으로는 병목을 해결하기 어렵다.

락 범위를 확대하면 데이터 정합성은 보장할 수 있지만,
동시 요청이 증가할수록 처리량은 감소할 수 있습니다.

### 경쟁이 발생하는 위치가 중요하다.

트랜잭션 내부가 아니라
Redis Atomic Counter에서 먼저 경쟁을 처리함으로써
DB 부하를 크게 줄일 수 있었습니다.

### 요청 처리와 영속화를 분리하는 것이 효과적이었다.

사용자 요청 처리와
DB 저장 작업을 분리하여
응답 성능과 처리 안정성을 함께 확보할 수 있었습니다.
